# Release evidence gates

A KalaReach release is made against seven evidence gates. This page names each gate, the evidence
that closes it, and the commands and suites in this repository that produce that evidence. Each
command produces the part of the evidence its own header describes. A result that no command here
can produce, such as audio after a hardware screen lock on a handset, comes from a run on the
platform itself.

Nothing on this page records that a gate is closed. It says what closes one.

| Gate | Evidence that closes it | Commands and suites that produce it |
| --- | --- | --- |
| Pairing and security profile | A frozen review of the implementation and its build, the remediation of what it finds, and positive and negative cross-language vectors | The vectors under `fixtures/pairing` and `fixtures/crypto`, generated by `kr-pairing-vectors` and `kr-crypto-vectors` and recomputed in TypeScript by `packages/protocol/test`. The review is the exception recorded below |
| Managed shells and terminal engine | Qualified binaries and module trees, reader races, the canonical profile and terminfo, and continuous direct, projection and input tests | `scripts/build-shells.sh` and `scripts/e2e-fence.sh` with the corpus under `tests/shells/`, `kr-shell-fixtures --check`, `kr-term-fixtures --check` and the terminal engine's tests in `crates/kr-term/tests` ([qualification](../shell-integration/qualification.md)) |
| Supported agents and plugins | A capability matrix for each distribution and version, native degradation, and response and composer arbitration fixtures | `tests/e2e/agents`, which runs the bundled connectors' qualification cases against vendor builds started from a managed shell, the application matrix of the conformance report, and in the plugin repository the qualification records under `fixtures/agents` and each package's `fixtures/conformance.json` |
| Native desktop and mobile platforms | Signing and permission results, nested Jobs, input methods, push, background calls and network transitions, taken on the platforms themselves | `scripts/e2e-desktop.sh`, `scripts/e2e-permissions.sh`, `scripts/e2e-wsl.sh`, `scripts/e2e-mobile.sh` and `scripts/e2e-voice-device.sh`, each of which says in its header what it cannot prove, the Windows signing gate ([windows-signing](windows-signing.md)) and the floors read back from each executable ([platforms](platforms.md)) |
| Model profile | Memory and processor figures on the reference host, useful output, and load and staleness tests; any alternative profile qualified independently | `scripts/bench-descriptions.sh` and `kr-describe-bench` for the figures, and the description service's tests in `crates/kr-describe/tests` and `crates/kr-describe-model/tests` |
| Managed services | Concurrency, forced-failure and coordinated-restore evidence for the ledger, relay, pairing, voice and storage services | The web repository's suites for each service, and the legs here that run a client against a deployment: `scripts/e2e-deployment.sh`, `scripts/e2e-m1b.sh`, `scripts/e2e-backup.sh` and `scripts/e2e-privacy.sh` |
| Recovery and the change-set flow | Restore from the recovery kit alone, privacy races, exact-version test and review, and filesystem-race fixtures | `scripts/e2e-backup.sh` and `scripts/e2e-privacy.sh`, and the change-set and project tests in `crates/kr-changeset/tests` and `crates/kr-project/tests` |

## How the evidence is read

`scripts/run-conformance.sh` runs the groups the platform supports and writes one result keyed by
identifier, with the commit it ran on and whether the tracked files differed from that commit. A
requirement that no test names appears in it as one with no test. The report records what each test
came to; it does not decide whether a release may be made. The gates are read against its result and
against the other commands in the table, one gate at a time, because no gate's evidence stands in
for another's.

## The pairing review exception

The first gate asks for an external review of the pairing profile and of the build it runs in. This
release is made without that review. Nobody outside the project has reviewed the short-code profile,
the source of the `spake2` crate it uses, that crate's side-channel behaviour or this repository's
use of it, and the owner of the product decided to release without it. The release makes no claim
that the exchange is constant-time, and the crate's own documentation says it probably is not and
that no independent security audit of it has been made.

What the release relies on instead is stated in [the pairing
reference](../pairing/README.md#the-pake-profile) and held by tests. The PAKE is the pinned
library's own, with no code of this repository standing in for it:
`every_cryptographic_library_is_pinned_and_the_pake_is_the_librarys` in
`crates/kr-crypto/tests/libsodium.rs` pins it exactly and shows that `kr-pairing` alone depends on
it, and `the_pairing_exchange_is_the_spake2_librarys_own` in `crates/kr-pairing/tests/pake.rs`
completes an exchange between this crate's side and the library driven on its own, in both roles.
The vectors in `fixtures/pairing` are regenerated and checked by `kr-pairing-vectors --check`, and
recomputed in TypeScript. Around the PAKE, five failed confirmation tags spend an invitation, an
invitation lasts five minutes, and no device is paired without a fresh owner confirmation of the
exact transcript.
