# App Store privacy answers for the iOS companion

This page includes the answers to the App Store privacy questions for the iOS companion (bundle identifier `to.kala.reach`). Use these to answer the questions for your developer account in App Store Connect; no build enters them. These answers are based on the privacy manifest in `apps/companion/src-tauri/gen/apple/companion-tauri_iOS/PrivacyInfo.xcprivacy` and on the code named beside each answer.

KalaReach can be built for release on the Simulator with `scripts/ios-privacy-manifest.sh`. That script will fail if the app links to any binary that uses APIs that are part of a required reason API category that is not listed in the bundle privacy manifest for that binary, or if the app's bundle privacy manifest lists a category that the main executable in the app bundle does not use. It can not be used to validate the answers to these data questions though, so if data the application collects changes, this must be updated. It also cannot tell which attributes a call to `getattrlist` asks for, so a File Timestamp declaration can hide a Disk Space use through that call. It should be run if anything that may change the dependencies of the application changes or any code that interacts with files, system clocks, or user defaults. It can only check the Simulator application, so `pnpm -C apps/companion privacy-manifest path/to/KalaReach.app` should also be run with the application from the archive before each upload, because the archive links the same Rust and Swift code built for the phone, and code that depends on the Simulator can differ.

The answer to "Do you or your third-party partners collect data from this app?" is Yes, and the answer to the question about tracking is No. For each of the data types in the table below, select that data type and answer the additional questions as its columns say. For data types not in the table, no data is collected, and the section on data that is not collected gives the reason for the types a reader would expect.

The first nine rows of the table are collected by KalaReach's own services or by the voice provider, and the Device ID and Other Diagnostic Data rows also include the Google libraries' entries. They are linked to an account or a device, and so to a person. Name is only collected if signing in with an organisation. None of them are used for tracking. The last row is from libraries from Google, as reported in their bundle privacy manifests. Their bundle privacy manifests also list Analytics as a purpose for Other Diagnostic Data, so both are listed. The app’s bundle privacy manifest doesn’t need to list them, but the label here does need to list what third parties collect. Xcode can also make a privacy report for an archive: choose Product, Archive, then Generate Privacy Report from the context menu for the archive in the Organizer. The entries there should be compared to the entries here before each submission.

This application doesn’t perform tracking. It doesn’t link AdSupport or AppTrackingTransparency, it has no advertising library and no analytics product, and it doesn't send data to any data broker. `NSPrivacyTracking` is false and `NSPrivacyTrackingDomains` is [] in the application’s bundle privacy manifest and the bundle privacy manifest for each package in the application.

Signing in, making voice calls, syncing settings, and account recovery are all opt-in, and the app can be used without any of these features. However, per Apple's guidance, since what the app collects depends on whether the user opts in to these features, all data collected by these features must be disclosed.

## Data that is not collected

Terminal output, prompts, session text, files, and photos are transferred between the user’s phone and hosts that the user owns over an encrypted connection. A managed relay may forward those bytes between the two endpoints when no direct path exists. The relay forwards the bytes as they arrive, but doesn’t keep them, only counting how many it receives. Drafts and settings that the user chooses to sync, and the recovery bundle, are sealed on the phone with a key that the sync service doesn’t have, so it only stores data that can’t be read. Apple counts data stored in a readable form, so sealed data is not collected in its sense. Camera and photo permissions are used to attach photos and video to sessions on hosts that the user owns.

This application doesn’t request or read location, contacts, health, fitness, financial or sensitive information, browsing or search history, or gameplay data. Purchases are made on the website. This application shows usage information, but it doesn’t have a checkout form or accept payment information. The account service keeps the network address and the user agent of each sign-in request in the session record. A session expires after seven days of use, or thirty days after it started at the latest, and a scheduled purge then deletes the record. The daily export of the account database holds a copy for up to thirty days longer, encrypted with a key the operator holds. IPv4 addresses are stored whole. IPv6 addresses are truncated to the first 64 bits. This is why Device ID and Other Diagnostic Data are linked to a person or device. The account and push rate limits keep a cryptographic digest of a network prefix. The relay rate limit keeps the prefix itself in memory for 60 seconds. The pairing room keeps a network prefix only while a socket is attached to it.

## Required reason API

Each Mach-O file in the built release application bundle has been scanned for the use of the APIs in each category listed by Apple. The built application contains three Mach-O files: the executable, `WebRTC.framework` and the notification service extension. The executable uses file timestamps, system boot time and user defaults. `WebRTC.framework` uses file timestamps and system boot time. The extension uses none of the categories, and none of the three uses disk space or active keyboards. Some of the APIs Apple lists, such as `fstatfs` and `fstatvfs`, are not used. They are referenced in unused functions of the `rustix` crate, and when the release version is linked the unused functions are dropped. A debug build keeps these unused functions, and only the release version is used in the application, so only the release build is held to the manifest.

| Category | Reason | Apple's text | Use in the application | Binary |
| --- | --- | --- | --- | --- |
| File timestamp | `C617.1` | "Declare this reason to access the timestamps, size, or other metadata of files inside the app container, app group container, or the app’s CloudKit container." | `stat`, `lstat` and `fstat` through the Rust standard library and the `rustix` crate, called by `kr_ipc` for private directories, owner-only files, the descriptor directory and the installation record, and by the drafts store, settings, the recovery record, sync membership, Tauri's lookup of its resource directory and the standard library's backtrace symbolizer, which maps the application's own executable. Tauri's opener plugin is linked and its path scope check imports `lstat`, but the application opens addresses only and no capability grants the plugin's path commands. | `KalaReach` |
| File timestamp | `3B52.1` | "Declare this reason to access the timestamps, size, or other metadata of files or directories that the user specifically granted access to, such as using a document picker view controller." | `NSFileModificationDate` in the dialog plugin's file picker (`FilePickerController.getModifiedAtFromUrl`), for the file the person chose. The mobile capability lets the page call the plugin's open command. | `KalaReach` |
| System boot time | `35F9.1` | "Declare this reason to access the system boot time in order to measure the amount of time that has elapsed between events that occurred within the app or to perform calculations to enable timers." | `ProcessInfo.systemUptime` in `CallAdapter`, which measures how long a voice call's owner has been silent so that a call whose owner has gone ends. Nothing derived from it leaves the device. | `KalaReach` |
| User defaults | `CA92.1` | "Declare this reason to access user defaults to read and write information that is only accessible to the app itself." | `NSUserDefaults` in Firebase Core, which keeps its data collection switch and its logging mode there, and in GoogleUtilities' wrapper around it. The application's own code does not use user defaults. | `KalaReach` |

`WebRTC.framework` includes its own privacy manifest, and reports use of the system boot time (`35F9.1` and `8FFB.1`) and file timestamp (`C617.1`) categories (`mach_absolute_time` and `stat`, respectively). The notification service extension does not import any of the APIs listed by Apple, and does not require a privacy manifest.

Two uses have no reason in Apple's list: each reads the type or size of a file that is outside of the container and that wasn’t selected by the user, and neither reads the file’s timestamp. The libsodium library uses `/dev/urandom` as its random source, and uses `fstat` on it to ensure it is a character device. This happens on `sodium_init` -> `randombytes_stir` -> `randombytes_sysrandom_stir`. The Rust standard library reads the version property list file when asked to determine the version of the operating system (on the phone this only happens if the first attempt with `sysctlbyname` fails; on the Simulator this is always done). This is called from Objective-C code in these packages via `__isPlatformVersionAtLeast`. The standard library uses `fstat` on the file to determine how large a buffer to allocate when reading the file. The file timestamp category is declared for the container metadata above, and these two uses are stated here and not given a reason they do not match. Apple's route for a use its list does not cover is to ask for a new approved reason, or to remove the use.

## Packages that need their own manifest

Apple lists the following libraries that are included in this app as needing to include a privacy manifest, and to be signed if they are included as binary dependencies. These are all included as source packages via the Swift Package Manager, with the revision pinned to the given revision. As such, these are not binary dependencies, and don’t need to be signed. Each does need to ship with a privacy manifest, which is done by including the manifest as a resource bundle at the root of the application bundle. The check will fail if any of these libraries that have a bundle of their own ship it with no manifest, or with a manifest that is not valid. It also reads every other manifest in the bundle. Nine of the packages' manifests have an empty list of accessed APIs, which Apple's technical note TN3181 lists as invalid; the packages' authors ship them, and the check reports them as notes and not failures.

Although the WebRTC library (revision `4266157cd08f` from the `stasel/WebRTC` package) is a binary framework, it is not listed by Apple. It does contain a privacy manifest, which is bundled in the app in the `Frameworks/WebRTC.framework` bundle. As an embedded framework, the build process signs it, because it isn’t signed when downloaded. The Firebase package causes the GoogleAppMeasurement package to be resolved, but that library is not linked into the app, and isn’t included in the application bundle. No analytics product is included in the application bundle.

Apple’s App Store Connect interface requires a URL at which a privacy policy is published. Their App Review Guidelines (5.1.1 (i)) also state that a link to the privacy policy needs to be included in the app. The privacy policy needs to state the same practices as are stated on this page. The “Privacy Choices” field is a URL to a page with information on how people can manage their data, and is optional.

These answers rely on four facts that aren’t stored in this repository, and whoever enters them should confirm each before submitting this app. First, the account service keeps the network address and the user agent of each sign-in request in the session record. This is a default setting in the account library it uses, and it hasn’t been turned off. Second, the voice provider's abuse-monitoring retention is thirty days, as the provider profile in the web repository states. Third, the managed broker discards transcript and audio events before it writes anything. Fourth, the first upload may name invalid privacy manifests in an email, and the nine packages' manifests above are the ones to expect in it.
