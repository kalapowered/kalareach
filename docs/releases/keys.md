# Signing keys and who rotates them

KalaReach keeps four families of signing key apart: the keys that sign releases and updates, the
catalogue's trust roles, the service's admission key and each organisation's policy key. No key
serves two of them. This page names each key, where its private half is held, where its public half
is pinned, who rotates it and how it is recovered. The owners are roles, as they are in the
website's record of what an operator supplies; the person who holds a role is the operator's to
name.

| Key | What it signs | Where the private half is held | Where the public half is pinned | Rotation owner | Rotation and recovery |
| --- | --- | --- | --- | --- | --- |
| Update channel root keys and release keys | The manifest of each host release, by a threshold of the release keys the root names for its targets role, and the next version of the root | The release keys are to be held in hardware-backed signing services and the channel roots on offline media; none exists yet, and the job that signs a release stops at the step that needs them ([the release manifest](manifest.md#publishing)) | `share/update-root.json` in each release: a host trusts the newer of the root of the release it runs and the root it recorded at its last switch | Release owner | A release carries the root or the next one, signed by a threshold of the current root's keys as well as its own ([Updating a host](../host/updates.md)). A key below the threshold that is lost or leaked is dropped by such a rotation. If the threshold of the current root's keys is lost, no update can move a host to another root, and if it is leaked, whoever holds it can sign an update that the host accepts. In both cases a host takes another root only through a fresh installation in a new store, because `kr host install` refuses a store that already has a current release; the written procedure for a host owner is a part of the key ceremony, which has not been held, and no such key exists to lose yet. A host whose current release carries no root and that recorded none at an earlier switch has no key to check another release against, and `kr host update` refuses every archive there |
| macOS Developer ID identity | Every Mach-O file of a macOS release tree (the Developer ID signature, with the hardened runtime) | Not set up yet. The release job reads the identity from the repository variable `APPLE_SIGNING_IDENTITY` and the certificate and its password from the secrets `APPLE_DEVELOPER_ID_CERTIFICATE_P12` and `APPLE_DEVELOPER_ID_CERTIFICATE_PASSWORD`, behind the `release-signing` environment; a macOS release stops at the first of them that is empty | The Apple certificate chain to Apple's root, which a host's operating system checks; the identity is public | The project owner, who sets the identity up | The Apple developer account can revoke and reissue the certificate. No step of this repository recovers a lost private key: it is replaced by issuing a new certificate, putting it into the secrets and signing the next release with it |
| macOS notary API key | The notarisation request for each macOS archive | Not set up yet. The release job reads the key from the secret `APPLE_NOTARY_API_KEY_P8` and its key and issuer identifiers from the repository variables `APPLE_NOTARY_KEY_ID` and `APPLE_NOTARY_ISSUER_ID`, behind the `release-signing` environment; the notarisation step stops at the first of them that is empty | Apple's notary service, which holds the key's public half for the account; no host checks it | The project owner | The key authenticates only requests to Apple's notary service, so a leaked key cannot sign a release. A lost or leaked key is revoked in the Apple developer account and replaced by a new key and new secrets; reissuing the Developer ID certificate does not replace it |
| Apple distribution identity and provisioning profiles | The signed iOS app, its notification extension and its test runner | Not set up for a release. A person signs a build by hand with an identity kept in a keychain on the build machine, named by its SHA-1, and the provisioning profiles ([the companion build](../client/mobile.md)); no workflow or secret of this repository holds one | Apple's certificate chain to Apple's root, which iOS checks, and the team identifier and bundle identifier that the website lists in its Apple app association document | The project owner, who holds the Apple developer membership | The Apple developer account can revoke and reissue the certificate and the profiles. No step of this repository recovers a lost private key: it is replaced by issuing a new certificate and signing the next build with it |
| Android upload key and Play App Signing key | The signed Android app bundle | Not set up. No workflow of this repository builds or signs an Android release bundle. The upload key is to be held by the owner of the Android app signing key, and the app signing key by Google under the app's Play Console record | The SHA-256 fingerprints of the certificates that an installed build is signed by, which the website lists in its Android app-link document (`ANDROID_APP_FINGERPRINTS`) | The owner of the Android app signing key | No step of this repository recovers either key. A lost upload key is replaced through the Play Console; the fingerprints the website lists are changed when the certificate an installed build is signed by changes |
| Windows code-signing identity | Every Windows executable and PowerShell package a release publishes | Azure Artifact Signing, in hardware security modules that do not give the key up; no secret or certificate credential exists | The Authenticode chain to the Microsoft root, with each signature timestamped; the identifiers are public | The Azure subscription owner for the profile and its role, the Entra application administrator for the application and its federated credential, the GitHub repository administrator for the environment | [Rotation and recovery](windows-signing.md#rotation-and-recovery) names each case, the incident steps and the recovery of a lost account |
| Release matrix signing key | The matrix of client, relay and discovery versions that work together, which the website publishes | The website's Worker secret `RELEASE_MATRIX_SIGNING_KEY` | The public half is published beside the matrix at `GET /api/release-matrix`, for whatever verifies it | Release owner | The website's deployment record, under "The release matrix" and "Credential rotation" |
| The catalogue's root, targets, snapshot and timestamp keys | Each generation of the signed plugin catalogue | None exists yet for production (the host's committed production root keys are empty). Each is to be generated on the machine that will hold it, in a signing directory outside every repository tree, and never kept in a repository: the pipeline refuses to sign with a key it finds in a tree and reads each key from a file in that directory. Which machine and which store hold the production keys is decided by the key ceremony, which has not been held. The development generation committed in the catalogue repository is a fixture signed with development keys that anybody can generate | `root.json` of a generation, which a host adopts out of band. A build seeds its bundled catalogue generation only against root keys it commits: a shipped build commits none, and a build with debug assertions commits the development generation's, which `bundled-plugins.lock` names | Release owner | A new root is signed by the root it replaces, and a host carries verification forward from the root a sync ended on ([Repositories and the catalogue](../plugins/catalogue.md)). A key that reached a commit is rotated by publishing a new root. A lost or leaked key of the targets, snapshot or timestamp role is replaced the same way. If the root's key is lost or leaked, no new root can be signed over it: a host then trusts a new root only when its owner adopts it out of band (`catalogue.remove` and `catalogue.add`, [the catalogue guide](../plugins/catalogue.md)), and a build commits the key identifiers of the root it seeds from. The written procedure is a part of the key ceremony, which the release owner holds |
| The service admission key | Every relay lease the website signs | The website's Worker secret `RELAY_ADMISSION_SIGNING_KEY` | `RELAY_ISSUER_KEYS` on each relay, and `GET /api/relay/issuer` | Network operator | Pin the new key on the relays, replace the secret with a higher revision, let installed leases expire or be revised, then unpin the old key; the website's deployment record gives the four steps under "Rotating it" |
| An organisation's policy-signing key | The organisation's membership leases, its policy and the links of its key chain | The organisation's own authority object in the website's service, generated there and never leaving it | The chain a host verifies when it enrols with the organisation: the host anchors at the last revision that chain carries and follows later revisions forward from it | The organisation's owner, through `POST /api/account/organisations/:id/policy-authority/rotate` | Rotation signs the successor with the key it retires and destroys the retired private half in the same transaction, so hosts follow the chain forward. The key is in no export. If the authority object's state were lost, its next use would create a new first revision, which an enrolled host refuses as a chain that lacks its anchor, until it is withdrawn and enrolled again. A host that never saw a rotation cannot tell a retained retired key's statement from a legitimate one, so a host that must detect a compromised predecessor needs evidence from outside the chain ([Account authority objects](../protocol/README.md#account-authority-objects)) |

Each key is generated, held and pinned on its own, and none can sign what another signs. A host
checks an update only against the channel root it trusts, which is the newer of the root of the release it runs and the one it recorded at its last switch, and a catalogue only against the
root it adopted; a relay checks a lease only against the issuer keys it pins; and an organisation's
lease or policy only against the chain the host enrolled for that organisation. A catalogue root
that named one key for all four of its roles is refused by the pipeline that builds it.

No private key or official credential is written in a repository. `scripts/check-release-secrets.py
scan --tracked` refuses a private key, a raw key seed or an official credential in this repository's
tracked files on every change, the catalogue pipeline refuses to sign with a key inside its own
tree, and the website's `pnpm records:check` refuses a private-key block, a live provider key and
files named for key material in the commits and the bundle it sends.
