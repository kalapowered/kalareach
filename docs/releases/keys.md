# Signing keys and who rotates them

KalaReach keeps four families of signing key apart: the keys that sign releases and updates, the
catalogue's trust roles, the service's admission key and each organisation's policy key. No key
serves two of them. The model-profile key, which signs only what is compiled into the host, is listed too. This page names each key of those families, where its private half is held, where its public half
is pinned, who rotates it and how it is recovered. The owners are roles, as they are in the
website's record of what an operator supplies; the person who holds a role is the operator's to
name.

| Key | What it signs | Where the private half is held | Where the public half is pinned | Rotation owner | Rotation and recovery |
| --- | --- | --- | --- | --- | --- |
| Update channel root keys and release keys | The manifest of each host release, by a threshold of the release keys the root names for its targets role, and the next version of the root | The channel the macOS and Linux host releases are signed under has one root, `release/tester-channel/root.json`, and two Ed25519 release keys that must both sign. The two release keys are secrets (`RELEASE_CHANNEL_TARGETS_KEY_1` and `_2`) of the `update-signing` environment, which one job of `release-host.yml` reads after a person approves the deployment; the root's own, snapshot and timestamp keys are kept by the project owner outside every repository and every service of the project, and the two release keys are also files of mode 0600 on the machine that made them, beside the root's own keys. No Windows manifest is signed under any channel: `release-windows.yml` takes no release key, and its step that signs a manifest ends the job with an error. The channel meant for the Windows archives is a separate production channel, whose release keys must be held in hardware-backed signing services and whose roots on offline media. `kr-release sign` reads its keys from local PKCS #8 files (`--key`; the channel's Ed25519 keys are such files), so a hardware-backed service needs a signing path that `kr-release` does not have | `share/update-root.json` in each release: a host trusts the newest of the root of the release it runs, the root it recorded at its last switch and the roots of an update still recorded or one that failed | Release owner | A release carries the root or the next one, signed by a threshold of the current root's keys as well as its own ([Updating a host](../host/updates.md)), and its manifest is signed by a threshold of the release keys the current root names for its targets role. A host checks each manifest against the release keys of the root it already trusts, so the root keys alone sign no update a host accepts. A rotation therefore needs both thresholds to be met by keys that are still held. A lost or leaked key is dropped by a rotation only while enough of the current root keys and enough of the current release keys remain to sign it, and a role whose threshold equals its number of keys, as the development generator makes the root role (one key of one) and the targets role, has no key to spare. If too few of the current root keys remain to meet the root's threshold, no successor root can be signed, and a host takes another root only through a fresh installation in a new store, because `kr host install` refuses a store that already has a current release; a fresh installation trusts the root of the release it installs. If too few release keys remain to meet the targets threshold, no archive can be signed, a replacement included, and the same fresh installation is the way out. If root keys leak but fewer than the threshold, the owner rotates at once, in a release that the current release keys sign. If a threshold of the root keys leaks, its holder can sign a successor root but no release a host accepts, and the owner rotates in the same way. If a threshold of the release keys leaks, its holder can sign releases that hosts accept until a rotation reaches them, and a host that installed such a release needs a fresh installation. The written procedure for a host owner is a part of the key ceremony. A host installed from the macOS and Linux channel above takes the production channel by a fresh installation in a new store, because no command in this repository writes a successor root. A host whose current release carries no root and that recorded none at an earlier switch has no key to check another release against, and `kr host update` refuses every archive there. A Windows host keeps no store of releases and `kr host update` does not run there, because its installer replaces the release, so no Windows host checks a channel root |
| macOS Developer ID identity | Every Mach-O file of a macOS release tree (the Developer ID signature, with the hardened runtime) | `Developer ID Application: Kala Holdings Inc (L775WGST9V)`: the private key (PKCS #8), the certificate and Apple's intermediate certificate are files of mode 0600 under `~/.config/kalareach-secrets/apple` on the machine that runs `scripts/sign-macos-release.sh`, read by path. None is a secret of a GitHub environment, none is imported into a keychain, and the script refuses a file of another mode, a certificate of another team or one that expires within 30 days | The Apple certificate chain to Apple's root, which a host's operating system checks; the identity is public | The project owner | The certificate is valid until 2027-11-27. The Apple developer account cannot revoke a Developer ID certificate: the owner asks Apple to revoke it by email to `product-security@apple.com`, and Apple's revocation stops users installing any app the certificate signed, so a release it signed that must stay installable is released again from a new commit with a new certificate ([the recovery steps](macos-signing.md#keys-and-replacing-them)). The account can issue further Developer ID certificates. A lost private key is replaced by issuing a new certificate for the same team; the project owner keeps a backup in their own store |
| macOS notary API key | The notarisation request for each macOS release tree (a ZIP of it) | The App Store Connect API key of the organisation's team (`.p8`, with `asc-api-key.json` naming its key identifier, issuer identifier and team): a file of mode 0600 beside the Developer ID files, read by `scripts/sign-macos-release.sh` and given to `xcrun notarytool` by path | Apple's notary service, which holds the key's public half for the account; no host checks it | The project owner | The key authenticates only requests to Apple's notary service, so a leaked key cannot sign a release. A lost or leaked key is revoked in App Store Connect, where the account's API keys are managed, and replaced by a new key and a new `asc-api-key.json`; reissuing the Developer ID certificate does not replace it |
| Apple distribution identity and provisioning profiles | The signed iOS app, its notification extension and its test runner | Not set up for a release. A person signs a build by hand with an identity kept in a keychain on the build machine, named by its SHA-1, and the provisioning profiles ([the companion build](../client/mobile.md)); no workflow or secret of this repository holds one | Apple's certificate chain to Apple's root, which iOS checks, and the team identifier and bundle identifier that the website lists in its Apple app association document | The project owner, who holds the Apple developer membership | The Apple developer account can revoke and reissue the certificate and the profiles. No step of this repository recovers a lost private key: it is replaced by issuing a new certificate and signing the next build with it |
| Android upload key and Play App Signing key | The signed Android app bundle | Not set up. No workflow of this repository builds or signs an Android release bundle. The upload key is to be held by the owner of the Android app signing key, and the app signing key by Google under the app's Play Console record | The SHA-256 fingerprints of the certificates that an installed build is signed by, which the website lists in its Android app-link document (`ANDROID_APP_FINGERPRINTS`) | The owner of the Android app signing key | No step of this repository recovers either key. A lost upload key is replaced through the Play Console; the fingerprints the website lists are changed when the certificate an installed build is signed by changes |
| Windows code-signing identity | Every Windows executable and PowerShell package a release publishes | Azure Artifact Signing, in hardware security modules that do not give the key up; no secret or certificate credential exists | The Authenticode chain to the Microsoft root, with each signature timestamped; the identifiers are public | The Azure subscription owner for the profile and its role, the Entra application administrator for the application and its federated credential, the GitHub repository administrator for the environment | [Rotation and recovery](windows-signing.md#rotation-and-recovery) names each case, the incident steps and the recovery of a lost account |
| The model-profile signing key | The detached signatures of the model profiles shipped in the host, which the host checks before it uses a profile | None kept: a key is generated when a shipped profile changes, signs both profile documents and is not kept ([the description model](../describe/README.md)) | `crates/kr-describe/profiles/signing-key.pub`, compiled into the host: the trust set a build ships is that key alone, and a profile document from outside the binary is accepted only with a detached signature from a key the host accepts | The author of the change to a shipped profile | Changing a shipped profile means generating a key, signing both documents again and committing the anchor with them in one change. The anchor ships beside the profiles, so a signature by it shows that a profile came from the build and not that anyone outside the build vouched for it |
| Release matrix signing key | The matrix of client, relay and discovery versions that work together, which the website publishes | The website's Worker secret `RELEASE_MATRIX_SIGNING_KEY` | The build: `PRODUCTION_PINS` in `crates/kr-client/src/services/matrix.rs` holds the one key a host trusts. The public half is also published beside the matrix at `GET /api/release-matrix`, and nothing reads that copy as a trust anchor | Release owner | A rotation is a release with the new key pinned, in this order: publish a matrix revision that already lists the coming release; replace the Worker secret; publish the release, whose publication step verifies the live matrix under the new key; installed builds take the key when they update. Until they do, an installed build refuses every new matrix and keeps the copy it holds. A leaked key is answered only by such a release. The website's deployment record gives the Worker's side, under "The release matrix" and "Credential rotation". Neither this page nor that record names a step that makes the key pair: it must be an Ed25519 pair made for the matrix and not the admission key's, and nothing compares the two seeds |
| The catalogue's root, targets, snapshot and timestamp keys | Each generation of the signed plugin catalogue | None exists yet for production (the host's committed production root keys are empty). Each is to be generated on the machine that will hold it, in a signing directory outside every repository tree, and never kept in a repository: the pipeline refuses to sign with a key it finds in a tree and reads each key from a file in that directory. Which machine and which store hold the production keys is decided by the key ceremony, which has not been held. The development generation committed in the catalogue repository is a fixture signed with development keys that anybody can generate | `root.json` of a generation, which a host adopts out of band. A build seeds its bundled catalogue generation only against root keys it commits: a shipped build commits none, and a build with debug assertions commits the development generation's, which `bundled-plugins.lock` names | Release owner | A new root is signed by the root it replaces, and a host carries verification forward from the root a sync ended on ([Repositories and the catalogue](../plugins/catalogue.md)). A key that reached a commit is rotated by publishing a new root. A lost or leaked key of the targets, snapshot or timestamp role is replaced the same way. If the root's key is lost, no new root can be signed over it: a host then trusts a new root only when its owner adopts it out of band (`catalogue.remove` and `catalogue.add`, [the catalogue guide](../plugins/catalogue.md)), and a build commits the key identifiers of the root it seeds from. If it is leaked, its holder can sign a successor root, which a host that syncs from the network follows at its next sync without its owner: the release owner rotates at once, and a host that may have followed another root re-anchors in the same two steps. The written procedure is a part of the key ceremony, which the project owner holds |
| The service admission key | Every relay lease, pairing admission and lease revocation the website signs | The website's Worker secret `RELAY_ADMISSION_SIGNING_KEY` | `RELAY_ISSUER_KEYS` on each relay; `GET /api/relay/issuer` reports the key to pin | Network operator | A planned rotation pins the new key on the relays, replaces the secret with a higher revision, lets installed leases expire or be revised, then unpins the old key; the website's deployment record gives the four steps under "Rotating it". A relay reads its pinned keys at start, so each change of the list restarts it and drops the connections through it: the overlap keeps leases from being refused and does not keep a relay from restarting. If the secret is lost, nothing signs a lease, an admission or a revocation until a new secret is installed and its public half is pinned. If the key leaks, its holder can sign leases and admissions that every relay pinning it accepts, so the operator installs a new secret, pins the new key and unpins the leaked one at once. Unpinning stops a relay taking anything else the leaked key signs, but a relay restores the leases it installed from its journal at its next start without checking the pins, so a lease the leaked key signed keeps forwarding until it expires or a revocation signed by a pinned key reaches the relay. A holder of the leaked key can also sign a revocation for a lease identifier it knows: the relay then refuses any other lease under that identifier, and the fence stays after the unpin, so that lease is allocated again under a new identifier. A holder of the leaked key can install leases on every relay that pins it, and the service has no record of such a lease: no route of the service revokes one, and a relay sets no limit on the lifetime a lease names, so such a lease ends only at the expiry its signer chose or when it has spent its allowance. No written step removes it before then, and a relay does apply a revocation signed by a pinned key for a lease it holds, at a revision above the lease's, so a lease named at the highest revision the relay's journal can store cannot be revoked. The relay does not restore a pairing admission when it starts |
| An organisation's policy-signing key | The organisation's membership leases, its policy and the links of its key chain | The organisation's own authority object in the website's service, generated there and never leaving it | The chain a host verifies when it enrols with the organisation: the host anchors at the last revision that chain carries and follows later revisions forward from it | The organisation's owner, through `POST /api/account/organisations/:id/policy-authority/rotate` | Rotation signs the successor with the key it retires and destroys the retired private half in the same transaction, so hosts follow the chain forward. The key is in no export. If the authority object's state were lost, its next use would create a new first revision. An enrolled host keeps the chain it holds and refuses each lease and policy the new key signs: a new chain whose head is not above the revision the host holds changes nothing, and one that is above it is refused as a chain that lacks the host's anchor, until the host is withdrawn and enrolled again. A host that never saw a rotation cannot tell a retained retired key's statement from a legitimate one, so a host that must detect a compromised predecessor needs evidence from outside the chain ([Account authority objects](../protocol/README.md#account-authority-objects)) |

The four families are kept apart: each has a key of its own, pinned in its own trust root, and none can sign what another signs. The release matrix key, the admission key and the organisations' authority objects are held by one Worker deployment, so those are apart as keys and not as deployments. No code compares the channel root's keys with the catalogue's or the two Worker seeds, so the separation rests on how each key is made and held and not on a check. Two exceptions are in the table: no written step makes the release matrix key, and a catalogue build holds the catalogue's four keys together in one signing directory. The page does not list a relay's own instance key, which signs its consumption receipts and is generated on the relay host, or the test issuer key a workstation holds for the end-to-end relay run. A host
checks an update only against the channel root it trusts (on macOS and Linux, the newest of the roots the first row names), and a catalogue only against the
root it adopted, followed forward through the successor roots a sync verified; a relay checks a lease against the issuer keys it pins when the lease is installed, and does not check them again when it restores the lease at its next start; and an organisation's
lease or policy only against the chain the host enrolled for that organisation. A root that names
one key for two of its roles is refused where each is read: an update channel root by
`kr-release verify` and by a host; a catalogue root by the pipeline that builds a generation (it checks every
root the generation ships) and by a host, when the owner is asked to adopt it, when the bundled
generation's root is trusted, and for the root a sync ends on before that root is kept. The
pipeline refuses a key in a spelling it cannot reduce to its bytes; a host compares the keys as the
TUF client parsed them, so in a root the pipeline did not build, one key written two ways is not
found as one, and the key ceremony reduces those. A root that names one key under two identifiers
in a single role is refused by `kr-release verify` and by a host, and the pipeline does not look for
it. The channel root names a key of its own for each of its four roles, the
snapshot and timestamp roles included, though a host verifies no signature by those two and does not require them. The release tool's and the host's comparison of a channel root look at the 32 bytes of each Ed25519 key, so neither finds a key's negation or a small-order shift of it. The catalogue pipeline's comparison reads the spellings of a key and finds the negation of an ECDSA key, which a host's comparison of a catalogue root does not; neither of those finds the negation or a small-order shift of an Ed25519 key. A host that holds an
update channel root made by an older `kr-release dev-keys`, which gave the root key to three roles,
is installed again in a new store.

No private key or official credential is written in a repository (the test fixtures hold test seeds, which sign nothing real), and four checks look for one, each with limits. `scripts/check-release-secrets.py scan --tracked` runs on a push to `main` and on a pull request, and the release workflows scan the tree and the proof archive their build job makes with the same script; no job scans the signed tree or the archives the Windows `release` job packs. It refuses a PEM private key, a private JSON Web Key, a file that is only a 32- or 64-byte seed (raw, in hex or in base64), a file named for a credential (an APNs key, a key store, an SSH key, a Firebase configuration file, a provisioning profile), a Google API key and a service-account document. It does not find a key in a binary encoding such as DER (the `.pk8` files `kr-release` writes and reads among them), a seed inside another file, or a secret that is not a key, and so it does not find the JSON object that holds a Worker key (`private_key` as an unpadded base64url seed); it reads no built app bundle, since no workflow scans an apk or an ipa. The catalogue pipeline refuses to sign with a key inside its own tree, and finds a key there by its PEM header or by a file name ending `.pem` or `.key`, among the files Git tracks or would add (a file Git ignores is not read, and the catalogue repository ignores `*.pem`, `*.key` and `signing/`). The website's `pnpm records:check` refuses a private-key block, a value that begins `sk_live_` or `whsec_`, and some file names (`.pem`, `.p8`, `.p12`, an `.env` file, a credentials file) in the commits and the bundle it sends, and it does not find the Worker keys' form either. `scripts/check-outgoing-records.py`, which this repository and the catalogue repository run on each push to `main` and each pull request, reads every commit of the range and refuses a private-key block that has a body, a value that begins `sk_live_` or `whsec_`, and the names of credential files, and it names the path and never prints the content.
